# Проверка готовности

Прими `TASK-ID`, `artifact_dir`, `proposal.md`, `spec.md`, итоговый diff, результаты автоматических проверок и известные ограничения. Веди отчёт и сообщения на русском языке, если правила проекта или репозитория явно не требуют другого языка. Если одного из ключевых входов нет, запроси его или явно зафиксируй ограничение.

Сопоставь фактическую реализацию со всеми Acceptance Criteria из `proposal.md`. Для каждой Acceptance Criteria дай вердикт `passed`, `partial`, `failed` или `not_checked` с evidence — конкретным тестом или ручной проверкой. Список вердиктов обязан покрывать все Acceptance Criteria без пропусков: критерий, который не проверялся, получает `not_checked` и отдельную запись в списке непроверенных сценариев с причиной. Проверь применимые сценарии:

* корректные и невалидные входные данные;
* пустые значения, `null`, границы и лимиты;
* обработку ошибок;
* обратную совместимость;
* поведение, которое не должно было измениться.

Ручные проверки выполняй по разделу «Необходимые проверки» из `spec.md` — команды запуска уже зафиксированы на этапе технического планирования. Если ручные проверки в spec не описаны, составь минимальный список сам из изменений по файлам. Каждую выполненную проверку фиксируй результатом с полями «название», «статус», «детали» (команда и фактический результат). Пропусти ручную проверку только если изменение тривиально, не содержит новой логики, надёжно покрыто автоматическим тестом и локальный запуск непропорционально сложен. Зафиксируй причину для будущего PR.

Если автоматическая проверка падает, сначала определи, воспроизводится ли падение без изменений задачи — на base-ветке или после временного отката diff. Падение, существовавшее до изменений, занеси в warnings с именем теста и не считай его провалом своей задачи.

Если проверку невозможно выполнить из-за окружения, явно сообщи:

> ⚠️ Не удалось проверить `{что}`. Для проверки требуется `{что необходимо}`.

Выполни self-review итогового diff:

* проверь соответствие `proposal.md` и `spec.md`;
* найди лишние изменения, очевидные баги и пропущенные edge cases;
* упрости решение, если это не меняет согласованный scope;
* оцени достаточность тестов и применимые security, performance, observability-риски.

Исправь найденные проблемы и повторно запусти затронутые проверки.

В конце запиши результат этапа в `{artifact_dir}/{TASK-ID}/stage-results/verification.json` по схеме `$dev-task-workflow/references/stage-result-schema.md`: `stage: "verification"`, `status`, `summary`, `artifacts` (изменённые файлы), `warnings`, при ошибке — `error` (код `test_failed`), `suggested_next` — `"code-review"` при успехе, `"back_to_implementation"` при `test_failed`. Затем верни DoD-отчёт: вердикт по каждой Acceptance Criteria с evidence, тесты, ручные проверки или причину пропуска, непроверенные сценарии, известные ограничения и готовность к внешнему review. Не выполняй внешний review, commit, push или создание PR.
