# Внешнее code review

Прими итоговый diff всех затронутых репозиториев, `proposal.md`, `spec.md`, результаты тестов и ручных проверок, а также известные ограничения. Веди замечания и итоговый отчёт на русском языке, если правила проекта или репозитория явно не требуют другого языка.

Внешний review выполняется для любого изменения, включая тривиальные: короткий diff не гарантирует отсутствия проблем.

## Независимый контекст ревьюера

Ревью проводит исполнитель с чистым контекстом — тот, кто не участвовал в реализации задачи и не видел хода её выполнения. Применяй первый доступный вариант каскада:

1. **Субагент харнеса.** Если харнес поддерживает субагентов, запусти ревью в субагенте с чистым контекстом: Claude Code — Task tool (встроенный `general` или кастомный агент из `.claude/agents/`); OpenCode — Task tool (встроенный `general` или агент из `.opencode/agents/`); Codex — субагенты. Запрети ревьюеру изменять файлы: только чтение кода и вывод замечаний.
2. **Отдельная сессия через CLI.** Если субагенты недоступны, запусти отдельную безконтекстную сессию агента (`codex exec`, `opencode run` или эквивалент) с тем же входом.
3. **Self-review с оговоркой.** Если недоступно и это, проведи self-review по чеклисту ниже, заново перечитав артефакты и diff. В summary результата этапа явно укажи `self-review`.

В запросе ревьюеру передай: diff, `proposal.md`, `spec.md`, результаты проверок, известные ограничения и чеклист:

* соответствие требованиям и Acceptance Criteria;
* корректность решения и обратную совместимость;
* баги, пропущенные edge cases и обработку ошибок;
* читаемость, нейминг, дублирование, сложность, coupling и cohesion;
* достаточность тестов;
* применимые security и performance-риски.

Используемую механику (`subagent`, `separate-session` или `self-review`) зафиксируй в начале `summary` результата этапа.

После review классифицируй каждое замечание как обязательное, рекомендательное или нерелевантное. Исправь обязательные замечания. Для отклонённых замечаний укажи краткое обоснование. Повторно запусти проверки, затронутые исправлениями, и обнови `spec.md`, если фактическое решение существенно изменилось.

Не создавай отдельный этап повторной self-reflection: достаточно проверить исправленный diff и связанные сценарии. В конце запиши результат этапа в `{artifact_dir}/{TASK-ID}/stage-results/code-review.json` по схеме `$dev-task-workflow/references/stage-result-schema.md`: `stage: "code-review"`, `status` (`ok` или `error`), `summary`, `artifacts`, `warnings`, при ошибке — `error` (код `review_required`), `suggested_next` — `"delivery"` при успехе, `"back_to_implementation"` при `review_required`. Затем верни список замечаний, принятые решения, повторные проверки и остаточные риски. Не выполняй commit, push или создание PR.
